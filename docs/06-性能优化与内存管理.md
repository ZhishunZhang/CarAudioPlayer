#三、四条主线（按问题分层）

 3.1 主线程零阻塞（驾驶场景的硬要求）

| 做法                                     | 位置                                |
| -------------------------------------- | --------------------------------- |
| Room 禁主线程查询（移除 allowMainThreadQueries） | AppDatabase.java                  |
| 收藏全异步（后台单线程池 + 主线程回抛）                  | FavoritesRepository               |
| 头像读盘 / 压缩 / 裁剪后台化                      | MineFragment / MainActivity       |
| 网络请求全走线程池（4 并发）                        | QQMusicApi                        |
| 图片下载与解码在固定线程池（6 线程）                    | ImageLoader                       |
| 列表绑定时零查库（收藏 mid 批量注入内存 Set）            | SongAdapter / FavoritesRepository |

3.2 网络与缓存

- **客户端两段式**：列表请求不带 resolveMid（秒回），播放时才解析那一首的 mid
- **服务端 midCache**：songId → mid 永久映射 + 并发 15
- **ApiCache 两级**：内存 Map + 磁盘文件，TTL 三档（搜索 10min / 榜单歌单 1h / 分类歌词 24h）
- **单飞合并**：缓存未命中时，同 key 的并发请求合并为一次（ConcurrentHashMap + CompletableFuture + computeIfAbsent）
- **getStale 兜底**：网络失败时用过期旧缓存，避免白屏
- **播放地址刻意不缓存**：vkey 会过期 → 改为回填 `song.playUrl` 走内存快速路径（切回 0ms）

 3.3 UI 渲染

- **播放状态拆流**：song（换歌）/ playing（播放态）/ progress（500ms 轮询）三条独立流，各页面按需订阅
- **ListAdapter + DiffUtil**：只重绑变化的行；当前播放高亮用 mid 比对去重，避免全表刷新
- **骨架屏**：网络慢时先占位
- **200ms 淡入 + 显式清 tint**：避免硬切与真人头像被罩灰
- **去过度绘制**：item 去掉同色背景重涂

 3.4 启动与资源

- **Application 懒加载**：启动阶段零重活
- **死代码清除**：删除 14 个文件

 四、内存管理

 4.1 防泄漏：视图生命周期

**背景**：Fragment 有两套生命周期且**不同步**——视图可能先销毁（onDestroyView），而实例还活着（在返回栈里 / 被复用）。

**风险**：`binding` 是 Fragment 的成员变量。若视图销毁时不置空，**活着的实例会强引用已经该回收的视图树**，而视图树里的每个 View 都持有 Context → 连带 Activity 一起收不掉，形成泄漏。

| 做法                                 | 位置                     | 说明                                                 |
| ---------------------------------- | ---------------------- | -------------------------------------------------- |
| `onDestroyView` 里 `binding = null` | **12 个 Fragment 全部实现** | 切断「实例 → 视图树」这条强引用链                                 |
| 订阅一律用 `getViewLifecycleOwner()`    | 全部 Fragment            | 观察者绑**视图**生命周期，视图销毁即自动解绑——消除「视图已销毁、实例还在」这段窗口期的 NPE |
| Activity 在 `onDestroy` 置空 binding  | MainActivity           | Activity 的视图与实例同生共死，不存在错位，故时机在 onDestroy           |

**附加收益**：置空同时是「哨兵」——视图销毁后若还有代码误访问 `binding`，会**立刻 NPE 崩掉**，问题当场暴露；否则会静默操作一棵僵尸视图树，最难排查。

### 4.2 主动释放（内存紧张时）

| 做法                                        | 位置                       |
| ----------------------------------------- | ------------------------ |
| 覆写 `onTrimMemory`，CRITICAL / 后台级时释放图片内存缓存 | App.java:50-54           |
| `clearMemory()` → `LruCache.evictAll()`   | ImageLoader.java:122-123 |

4.3 缓存上限（防无限增长）

| 缓存            | 上限                                                          | 实现                        |
| ------------- | ----------------------------------------------------------- | ------------------------- |
| 图片内存 LruCache | **可用堆的 1/8**（`maxMemory / 8`），按 `Bitmap.getByteCount()` 计大小 | ImageLoader.java:44-51    |
| 图片磁盘缓存        | 超过 **50MB** 时按 lastModified 从旧到新删到 **40MB**                 | ImageLoader.trimDiskCache |
| ApiCache 磁盘文件 | 靠 TTL 判过期；过期文件自动删                                           | ApiCache.java             |

 4.4 播放器与系统资源释放

| 资源           | 释放点                                                                |
| ------------ | ------------------------------------------------------------------ |
| ExoPlayer    | `PlaybackService.onDestroy` → `mediaSession.getPlayer().release()` |
| MediaSession | `PlaybackService.onDestroy` → `mediaSession.release()`             |

### 4.5 防 OOM（大图）

- **降采样解码**：先用 `inJustDecodeBounds` 只读尺寸（不分配像素），再按 2 的幂采样率解像素
- 封面统一按显示尺寸解码 + 裁圆，避免按原图尺寸分配
